## Routine A: Weekly Source-Metadata Check

**Cadence:** Monday 01:17 UTC / 09:17 SGT (owner-approved 14 September 2026).
**Primary path:** GitHub Actions workflow `source-metadata-weekly.yml` runs automatically.
**Owner action that day:** Review issue #34 and the terminal Actions run. A missing receipt
is unknown, not success.

### A1. What to check

- Did the weekly Actions run complete and post a comment to issue #34?
- Is the terminal run's checkpoint state `ready`?
- Are there any `exit 1` conditions: stale, unavailable, unsupported, missing-secret sources,
  pending notices, or deferred checks?
- Are the three credentials-required sources still in that state
  (Covered Linkway, Pedestrian Overhead Bridge/Underpass, Traffic Signals)?
- GitHub schedules are best-effort; public-repository inactivity can disable them after 60 days.
  A manual activation is not proof a natural cron ran.

### A2. Commands

**GitHub Actions path (primary):** No local command needed for the normal weekly run.
The Actions adapter posts results to issue #34 automatically.

**Local CLI — first run only (bootstrap, already done 14 September):**
```powershell
if ((Get-Location).Path -ne 'C:\sgSHIOK2026') { throw 'Wrong working root' }
$run = Get-Date -Format 'yyyyMMdd_HHmmss'
C:\sgSHIOK2026\.venv\Scripts\python.exe -B -m scripts.check_source_metadata --bootstrap --output "C:\sgSHIOK2026\qa\source-monitor\$run"
```
Do not use `--bootstrap` again. Bootstrap was used once on 14 September; using it again
to clear a fault is explicitly prohibited by README.md.

**Local CLI — subsequent runs (replace `--previous` path with the preceding run's state.json):**
```powershell
if ((Get-Location).Path -ne 'C:\sgSHIOK2026') { throw 'Wrong working root' }
$run = Get-Date -Format 'yyyyMMdd_HHmmss'
C:\sgSHIOK2026\.venv\Scripts\python.exe -B -m scripts.check_source_metadata --previous "C:\sgSHIOK2026\qa\source-monitor\<PRECEDING_RUN_LABEL>\state.json" --output "C:\sgSHIOK2026\qa\source-monitor\$run"
```
Exactly one of `--bootstrap` or `--previous` is required. Omitting both or supplying both
stops before catalog reads, requests, or output creation.

**Inspect an existing journal (read-only, no network):**
```powershell
python -B -m scripts.inspect_source_notice_journal --journal <absolute-journal-path> --journal-sha256 <retained-identity-sha256>
```

### A3. Interpreting exit codes and output

| Exit code | Meaning |
|-----------|---------|
| 0 | No current automatic-check attention condition. Not proof that physical conditions or payload bytes are unchanged. |
| 1 | Attention required: unknown, stale, unavailable, or unsupported sources; pending notices; deferred check; missing credentials. |
| 2 | Local integrity, state, or IO failure. Inspect the receipt. Do not retry blindly. |

For the Actions run: `exit 1` / Actions failure represents source attention, not a stopped
scheduler. The last known source breakdown (14 September first run) was: 14 observed +
3 credentials_required + 4 unsupported + 3 manual = 24 sources.

A changed publisher timestamp is a metadata signal, not evidence that dataset bytes changed.
A stable DataMall listing reference does not prove its payload is unchanged.

### A4. What "needs attention" looks like

- Actions run shows failure or no run completed on the expected Monday.
- Terminal run checkpoint is not `ready`.
- Exit 1 from the local CLI with sources newly moving to stale/unavailable/unknown.
- `exit 2`: local integrity or IO failure.
- `LTA_DATAMALL_ACCOUNT_KEY` missing (reported as `credentials_required`, not healthy).
- Deleted, expired, stopped, or conflicting history in the Actions artifact store.
- The Actions artifact is approaching bounds: 12,000 files, 64 MiB raw/ZIP, or 4,096
  lifetime notice requests.

### A5. Who to notify and how

Per the Ownership And Cadence table in README.md: the owner reviews issue #34 and the
terminal Actions run on Monday. The Actions workflow posts notices to issue #34 as
`github-actions[bot]` (numeric ID 41898282). No other notification channel is documented.

If the run is stopped or expired: investigate without deleting or reinitializing history.
Use a new manual dispatch only with an intact, ready predecessor. Never bootstrap again
to clear a fault. Preserve evidence and investigate.

If the issue is unavailable: an Actions failure remains visible. Missing receipts are
unknown, not success.

## Routine B: Daily Report-Cleanup Health Check

**Cadence:** Daily cleanup job runs at 01:17 Singapore time (17:17 UTC) with a 30-second
outer timeout. First natural daily execution was unobserved as of 18 September 2026.

**Note:** Resident report intake is currently disabled. No reports or usage rows are retained.
This routine monitors the cleanup job health only, not a live moderation queue.

### B1. What to check

- Did the daily cleanup job run and succeed?
- Check `shiok_reports.control.cleanup_failed_at` — is it populated?
- Check `shiok_reports.control.cleanup_verified_at` — is it present and recent?
- README.md explicitly warns: cron can report `succeeded` when the function caught a
  deletion failure and paused intake. Both fields must be checked.
- Is Supabase project `sgshiok` (`ztjilsfgoephcdcsgcks`) accessible and on Free plan?
  Low-activity pausing is possible on Supabase Free.

### B2. Command

```powershell
python -B scripts/collect_report_cleanup_health.py
```

This command requires `SHIOK_SUPABASE_ACCESS_TOKEN` set as a session-only environment
variable before running. Never put the token in command arguments, a tracked file, or
a public issue. The command verifies the dedicated project and Free organization, then
reads only cleanup/job diagnostics.

### B3. Interpreting exit codes and output

| Exit code | Meaning |
|-----------|---------|
| 0 | Healthy monitoring at observation time. Not permission to enable intake. |
| 1 | Attention required (also covers unobserved first scheduled run). |

Output contains health labels and observation times only, not reports or raw errors.
The command neither triggers cleanup nor changes settings.

### B4. What "needs attention" looks like

- `cleanup_failed_at` is populated (cleanup caught a deletion failure and may have paused intake).
- `cleanup_verified_at` is missing or stale.
- Exit 1 (including the case where the first scheduled run has not yet been observed).
- Supabase project is paused due to inactivity.
- Provider quotas are shared and should be rechecked if intake is ever activated.

### B5. Who to notify and how

Per the Ownership And Cadence table in README.md: the owner reviews the report
moderation queue weekly (only after T13-T18 activation) and responds promptly to
privacy/abuse incidents when noticed. The existing pattern is owner review plus
issue #34 for source-related notices. No separate notification channel for cleanup
health is documented. Record observations in `.agents/STATE.md` and durable decisions
in `decisions.md`.

If cleanup is unhealthy: keep intake paused. Cleanup outages and recovery copies can
extend physical retention. Apply expiry/deletion before reopening access.

## Routine C: Release / Deployment Readiness Check

**Cadence:** Each release candidate. Run before any Vercel publish attempt.
Release execution remains gated (T27/T28). No full-batch rescore or deployment is
currently approved to run without explicit owner approval.

### C1. What to check

- Are the shelter-map bundle and lamp overlay artifact present, internally consistent,
  and passing all readiness gates?
- Are there unresolved gates, warnings, or legacy provenance states?
- Is the gate verdict a pass (all checks) or a fail (any blocking condition)?

### C2. Commands

**Routine release review (gate verdict plus checks and warnings, no full nested report):**
```powershell
uv run python run.py readiness --gate-summary
```

**Full readiness report (before any Vercel publish attempt):**
```powershell
uv run python run.py readiness
```

**Before any full geocode, scoring, or release batch, also run:**
```powershell
uv run python run.py batch-plan
```

Do not use `run.py check` or its freshness/discovery variants for maintenance. The
standing prohibition on `run.py check` is documented in README.md.

### C3. Interpreting exit codes and output

The readiness check validates the shelter-map bundle and verifies the local lamp overlay
artifact is present and internally consistent. Legacy provenance (active bundle predates
P8-P10 record-level provenance) is reported as `legacy`, not `failed`, provided there is
no internal inconsistency. Internally inconsistent provenance is release-blocking `failed`.

Missing gzip companions or lookup files fail. Nothing is regenerated. Do not rebuild,
overwrite, or mutate existing public data directories to repair a missing artifact; copy
or create only a new versioned artifact after owner approval.

### C4. What "needs attention" looks like

- Any gate verdict of `failed` or `blocked`.
- Missing lamp overlay artifact (`web/public/data/lamp_posts_v1/`).
- Unresolved gates from T27/T28 (MapLibre security disposition T29, client upgrade
  acceptance, immutable-stage acceptance).
- Warnings about stale sources — report them; do not mutate frozen v1 in place.

### C5. Who to notify and how

Per the Ownership And Cadence table in README.md: the owner approves the exact release
candidate and target. A failed stage stops further action; inspect actual remote state
before retry or rollback. Assemble exact identities, tests, unresolved gates, and
rollback target before presenting to the owner.

Rollback: plan to the identified previous immutable production deployment. On Hobby,
Instant Rollback is limited to the immediately previous deployment. Confirm target
eligibility and configuration before owner-approved execution. See README.md "Failure
And Rollback Rules" for full detail.

After any approved release or rollback: test fresh, returning, and retained-tab clients.
A hosting rollback does not roll browser caches back.

## Routine D: Capacity and Free-Tier Usage Review

**Cadence:** First Saturday monthly, and before input changes or releases.
(Source: Ownership And Cadence table, README.md.)

### D1. What to check

- Vercel Hobby: current plan, billing period, Edge Requests used/remaining, transfer,
  function use, and headroom.
- Supabase Free: project `sgshiok` is accessible, on Free plan, not paused, and within
  quotas. Supabase Free does not include automatic backups or point-in-time recovery.
- Local payloads: are `.env`, `processed/`, `web/public/data/`, and QA directories
  still present? (No existing backup is assumed.)
- Is a private backup destination selected, with adequate capacity and encryption/key custody?

### D2. Commands

There is no single local command for this review. The checks are:

**Readiness summary (covers bundle and artifact presence):**
```powershell
uv run python run.py readiness --gate-summary
```

**Report cleanup health (covers Supabase project status):**
```powershell
python -B scripts/collect_report_cleanup_health.py
```

Vercel usage must be checked from the Vercel dashboard or API directly. README.md says:
> Check [Vercel's current usage policy](https://vercel.com/docs/limits/fair-use-guidelines),
> including Hobby's non-commercial restriction, instead of relying on old quota figures.

No local command for Vercel quota inspection is documented.

### D3. Interpreting output

Internal thresholds documented in README.md:
- 80% of Vercel Edge Request quota: owner review.
- 95% of Vercel Edge Request quota: hold optional releases and checks.

README.md states these are not provider guarantees or automatic shutdowns. They are
proposed internal thresholds only.

### D4. What "needs attention" looks like

- Vercel Edge Requests at or above 80% of the billing-period quota.
- Vercel Edge Requests at or above 95%: hold optional releases.
- Supabase project paused (low-activity pause is possible on Free).
- No private backup exists for the local payloads.
- Missing local payload directories that cannot be rebuilt without a separate approved run.
- Source metadata Actions artifact approaching bounds (12,000 files or 64 MiB).

If Vercel quota is hit: first check whether production is serving current `main`.
Automatic Git deployments are intentionally disabled in `web/vercel.json`; committed
cache and crawler reductions do not affect live traffic until the owner manually deploys.
Hard stops (pause/protect project, firewall deny rules, temporary attack mode) change
public availability or visitor friction and are owner decisions, not agent-default changes.

### D5. Who to notify and how

Per the Ownership And Cadence table in README.md: the owner checks free-plan usage,
owns a private backup destination and keys, and separately approves any restore drill.
No existing backup is assumed. Propose an additive snapshot scope to the owner; do not
sync deletions, prune old versions, or mutate the only source copy.

Record capacity observations in `.agents/STATE.md` and durable decisions in `decisions.md`.
